# Design: LocalAPI — OpenAI-Compatible Proxy for opencode

Generated by /office-hours on 2026-09-01
Status: APPROVED
Mode: Builder

## Problem Statement

You want to point any OpenAI-compatible tool (Cursor, Continue, etc.) at a local proxy server, and have it route requests to your opencode agent session. The proxy translates between OpenAI's `/v1/chat/completions` format and opencode's native API, so your existing dev tools "just work" with your agent.

## What Makes This Cool

Using an active AI agent session as the backend for a standards-compliant API. Any tool expecting OpenAI format suddenly works with your agent — zero integration work per tool.

## Constraints

- FastAPI-based, Python
- Dependencies: FastAPI + httpx + stdlib (3 total)
- Non-streaming only for v1
- Self-use: personal tool, not a product
- Under 200 lines of Python

## Premises

1. FastAPI server accepts OpenAI-format requests and routes them to opencode's native API
2. opencode serve is running (or started by the proxy) on localhost
3. The proxy translates between OpenAI and opencode's OpenAPI 3.1 schema
4. Stateless: each request creates a fresh opencode session (no conversation continuity)
5. Self-use: point Cursor/Continue at localhost

## Approaches Considered

### Approach A: Subprocess-per-request
- Spawns `opencode run [message]` per request, parses stdout
- Effort: S, Risk: Low
- Pros: Simple (~100 lines), no session management
- Cons: Cold start (~1-3s), heavy process spawn

### Approach B: Persistent process with IPC
- Start opencode once, communicate via pipes
- Effort: M, Risk: Medium
- Pros: Fast responses, conversation continuity
- Cons: Complex lifecycle, IPC fiddly, error recovery harder

### Approach C: opencode serve + translation (CHOSEN)
- Run opencode serve, translate OpenAI requests to its API
- Effort: S-M, Risk: Low-Medium
- Pros: Uses existing server, clean translation, no subprocess overhead
- Cons: Requires understanding opencode's API schema

**Fallback:** If opencode's API doesn't support what we need, fall back to Approach A (subprocess).

## Recommended Approach

**Architecture:**
1. Start opencode serve as subprocess on port 4096
2. FastAPI server on port 8000 (configurable)
3. `POST /v1/chat/completions` → translate to opencode format → translate back
4. `GET /v1/models` → query opencode providers → format as OpenAI models
5. `GET /health` → liveness check

**Model mapping:** Hard-coded dict mapping OpenAI model names to opencode provider/model IDs. Extend via config file later. Unknown models passthrough.

**Token counts:** Return `prompt_tokens: 0, completion_tokens: 0, total_tokens: 0`. Acceptable for v1.

**Error handling:** opencode errors → HTTP 500/503 with OpenAI-format error body.

**Session model:** Stateless. Each request creates a fresh opencode session.

**Request flow:**
```
Cursor → POST /v1/chat/completions (OpenAI format)
  → Proxy translates to opencode format
  → Proxy sends to opencode serve (localhost:4096)
  → opencode processes with configured provider
  → Response translated back to OpenAI format
  → Cursor receives standard OpenAI response
```
